# 2026-03-16 작업 기록

업데이트 기준: 2026-03-16

## 1) 오늘 작업 요약
- `/main`, `/`, `/detail`의 새로고침 및 뒤로 가기 기준 스크롤 복원 정책을 다시 정리했다.
- `/main`은 새로고침 시 정확한 위치 복원보다 전용 오버레이를 먼저 보여 주고, 뒤에서 화면을 함께 렌더하는 방식으로 방향을 바꿨다.
- `/`는 구간별 최소 복원으로 정리하고, hero는 최상단 기준, 나머지 구간은 절반 이상 넘어갔을 때만 해당 구간 상단으로 맞추는 방식으로 정리했다.
- `/detail`은 기본적으로 최상단부터 다시 시작하되, 새로고침 시 trailer나 row가 절반 이상 보인 경우에만 해당 구간 상단을 네비게이션 아래로 맞추도록 정리했다.
- 테스트 파일 이름과 문서 구조를 현재 목적에 맞게 정리했고, Firebase 설정과 보안 규칙도 함께 정리했다.

## 2) 주요 변경 사항
- `ScrollManager`와 라우트별 스크롤 정책을 정리하면서, `/main`의 복원 분기 로직을 줄이고 새로고침 전용 오버레이 중심 구조로 전환했다.
- `/main`에서 새로고침 시 footer를 먼저 찍고 올라오는 문제를 잡기 위해 오버레이가 보이는 동안 상단 기준을 유지하도록 조정했다.
- `/`는 픽셀 단위 복원이 아니라 구간 단위 최소 복원으로 바꿨고, top10, pricing, faq, footer는 네비게이션 높이와 여백을 반영해 상단 위치를 맞추도록 정리했다.
- `/detail`은 trailer와 row 구간이 늦게 붙는 경우까지 고려해, 해당 구간이 실제로 마운트될 때까지 기다린 뒤 조건에 맞으면 복원하도록 조정했다.
- 테스트 파일 이름을 아래처럼 목적에 맞게 바꿨다.
  - `tests/main-scroll-restore.spec.js` -> `tests/main-route-scroll-policy.spec.js`
  - `tests/scroll-restoration.spec.js` -> `tests/cross-route-scroll-policy.spec.js`
- `tests/debug-url-matrix.md`를 현재 확인 포인트 기준으로 다시 정리했다.
- Firebase 클라이언트 초기화 파일을 `src/firebase/index.js`로 정리하고, Firebase 설정 파일은 `firebase/` 폴더 아래로 모았다.
- 더 이상 쓰지 않는 `updates` 기능을 코드와 보안 규칙에서 제거했고, 관련 화면과 라우트도 함께 삭제했다.
- Firebase 디버그 로그가 루트에 떨어지지 않도록 명령 실행 위치를 `firebase/` 폴더 기준으로 바꿨다.

## 3) 테스트 및 검증
- `npm run build` 실행 결과 정상 통과했다.
- `src/components/__tests__/ScrollManager.test.jsx` 단위 테스트를 기준으로 스크롤 정책 변경이 깨지지 않는지 확인했다.
- 브라우저 시나리오 테스트 파일도 이름을 정리하고 실행 흐름을 다시 점검했다.
- 직접 확인한 주요 항목은 아래와 같다.
  - `/main` 최상단 새로고침 시 footer를 먼저 찍지 않고 오버레이 이후 상단 유지
  - `/main`에서 스크롤 후 새로고침 시 하단으로 튀지 않고 상단 기준 유지
  - `/`에서 hero, top10, pricing, faq, footer 기준 구간 복원 동작 확인
  - `/detail`에서 trailer, row 구간 새로고침 시 조건에 맞는 경우 구간 상단 복원 확인
- Firebase 보안 규칙은 실제로 다시 배포했고, 로컬에서 아래 권한을 직접 확인했다.
  - 일반 사용자: 본인 글만 수정 및 삭제 가능
  - 관리자: 모든 글 삭제 가능
  - 체험 계정: 읽기와 등록 가능
  - 보호 라우트 직접 접근 시 로그인으로 유도되는지 확인

## 4) 이슈 및 메모
- 오늘 가장 오래 붙잡은 문제는 `/main` 새로고침 시 footer를 먼저 찍고 올라오는 현상이었다.
- 이 문제를 디버깅하면서, 브라우저가 먼저 `index.html`과 CSS를 읽고 화면을 준비한 뒤 React가 다시 마운트된다는 점을 다시 체감했다.
- 특히 비동기 데이터가 늦게 붙거나, 이미지와 동적 콘텐츠의 실제 크기가 나중에 확정되면서 문서 높이가 뒤늦게 다시 바뀌는 상황이 스크롤 복원을 더 어렵게 만들었다.
- 결과적으로 모든 화면을 같은 방식으로 정확하게 복원하려 하기보다, 화면 목적에 맞게 정책을 나누는 편이 더 현실적이었다.
  - `/main`: 새로고침 전용 오버레이 중심
  - `/`: 구간 단위 최소 복원
  - `/detail`: 기본 상단 시작, 일부 구간만 조건부 복원
- 테스트는 많이 보강했지만, 브라우저 시나리오 테스트 기대값과 실제 체감이 완전히 일치하지 않는 부분은 추후 더 다듬을 필요가 있다.
- 오늘 작업을 하며 다시 느낀 점은, 스크롤 복원과 사용자 경험 개선은 무조건 더 정교하게 만드는 것이 답이 아니라는 것이다. 어떤 화면에서 어떤 흐름을 지켜야 하는지 먼저 정하고, 그 목적에 맞게 설계하는 편이 더 중요했다. 이번에는 모든 위치를 완벽하게 복원하는 것보다, 각 화면의 성격에 맞는 최소한의 타협을 통해 더 안정적인 사용자 경험을 만드는 쪽이 더 현실적인 해법이었다.
