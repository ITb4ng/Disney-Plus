# 상태 기반 UI 설계와 테스트 도입 경험

## 1. 문제 인식: API 의존도가 높은 UI 구조

이번 작업은 `feature/state-ui-stability` 브랜치에서 시작되었다.

프로젝트를 개발하면서 API 의존도가 높은 구조에서 UI가 대부분 성공 케이스 중심으로 설계되어 있다는 점을 발견했다. 이 구조에서는 
다음과 같은 문제가 발생할 수 있었다.

- API 요청 실패  
- 데이터가 없는 경우  
- 네트워크 지연 상황  
- 외부 CDN 이미지 로드 실패  

이러한 상황에서 UI가 적절히 대응하지 못하면 사용자 경험이 크게 저하될 수 있다.

따라서 단순한 데이터 렌더링이 아니라, 네트워크 상태에 따라 UI를 분기하는 구조가 필요하다고 판단했다.

---

## 2. 상태 기반 UI 설계

UI 안정성을 확보하기 위해 다음 네 가지 상태를 기준으로 UI를 분리했다.

- loading — API 요청 진행 중  
- success — 정상 데이터 응답  
- empty — 데이터 없음  
- error — API 요청 실패  

이 상태 구조를 기반으로 API를 사용하는 컴포넌트에 상태를 props로 전달하도록 구조를 변경했다.

부모 컴포넌트에서 상태를 관리하고, 하위 컴포넌트는 UI 렌더링만 담당하도록 역할을 분리했다.

이렇게 구조를 정리하자 컴포넌트의 책임이 명확해졌고 유지보수성이 개선되었다.

---

## 3. CDN 이미지 Fallback 처리

메인 페이지의 HeroSection에서는 CDN 이미지를 사용하고 있었는데, CDN 경로가 변경되거나 이미지가 삭제되는 상황을 고려해야 했다.

이를 대비해 이미지 로딩 실패 시 대체 이미지를 보여주는 fallback 처리 로직을 추가했다.

이를 통해 최소한의 레이아웃과 콘텐츠 흐름을 유지할 수 있도록 개선했다.

---

## 4. 상태 테스트 방식 개선

처음에는 API를 직접 수정하거나 요청을 차단하여 상태를 테스트할 방법을 고민했다.

하지만 개발 모드에서 URL 파라미터를 이용해 상태를 강제로 지정할 수 있는 방법을 발견했다.

예를 들어 특정 파라미터를 통해 loading, error 상태를 직접 확인할 수 있도록 했다.

이 방식은 상태 테스트 효율을 크게 개선했다.

---

## 5. 스크롤 상태 보존 문제 해결

URL 파라미터 기반 테스트를 진행하면서 새로운 문제가 발생했다.

라우트가 변경될 때마다 스크롤 위치가 초기화되는 문제가 발생한 것이다.

이를 해결하기 위해 라우트별 스크롤 위치를 저장하는 유틸 함수를 직접 구현했다.

덕분에 테스트 과정에서 스크롤 위치를 유지할 수 있었고 반복 테스트가 훨씬 편해졌다.

---

## 6. 테스트 코드 도입

Swiper 인덱스 상태 보존과 라우팅 로직이 복잡하게 얽히면서 일부 동작이 정상적으로 작동하지 않는 문제가 발생했다.

이 문제를 해결하기 위해 테스트 코드를 작성하기 시작했다.

문제가 되는 동작을 테스트 코드로 작성하고 검증하면서 보다 체계적으로 문제를 분석할 수 있었다.

또한 테스트 코드를 통해 현재 사이트의 문제 상황을 기록하고 앞으로 기능을 추가하거나 수정할 때 참고할 수 있는 기반을 마련했다.

---

## 7. E2E 테스트 경험

E2E 테스트 코드 자동화를 통해 사이트의 실제 사용자 흐름을 다시 확인할 수 있었다.

로그인 → 메인 진입 → 콘텐츠 탐색 → 상세 페이지 이동

과 같은 실제 사용자 시나리오를 기반으로 테스트를 구성하면서 서비스 전체 흐름을 다시 점검할 수 있었다.
