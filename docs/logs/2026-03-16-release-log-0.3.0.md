## 1. 작업 시작점: 스크롤 복원 문제를 다시 구조적으로 보기 시작함

이번 브랜치를 열고 첫 작업으로 다시 붙잡은 문제는 `Swiper` 페이지 위치와 라우트별 세로 스크롤 복원이 새로고침에서 일관되게 동작하지 않는 점이었다.

처음에는 단순히 "이전 스크롤 값을 저장하고 다시 올리면 되지 않을까"라는 방식으로 접근했지만, 실제 앱은 그렇게 단순하지 않았다.

- `/main`은 배너, 네비게이션 opacity 변화, row 비동기 렌더, footer 존재 여부가 모두 초기 레이아웃에 영향을 줬다.
- `/`는 hero, top10, pricing, faq, footer처럼 문서 흐름이 큰 섹션 단위로 바뀌는 구조였다.
- `/detail`은 hero, trailer, related row가 비동기 데이터에 따라 뒤늦게 생기고 사라졌다.

이 때문에 "숫자 하나 저장해 두고 그대로 복원"하는 방식은 실제 화면 체감과 자꾸 어긋났다.

## 2. `/main`에서 가장 오래 붙잡은 문제: 새로고침 시 footer를 먼저 찍고 올라오는 현상

처음 가장 거슬렸던 현상은 `/main` 최상단이나 아주 조금만 스크롤한 위치에서 새로고침해도, 화면이 잠깐 footer 근처를 찍고 난 뒤 다시 위로 복원되는 문제였다.

초반에는 이 현상을 `top`, `content`, `footer` 같은 UI 복원 모드로 나눠서 해결하려고 했다.

- 최상단이면 즉시 렌더
- 중간이면 콘텐츠 복원
- footer 근처면 footer 기준 복원

하지만 이 방식은 저장된 상태가 조금만 s안 맞아져도 잘못된 분기로 들어갔다.



실제 디버깅 중 겪은 문제는 아래와 같았다.

- 최상단인데도 이전 `footer` 모드가 남아 있어서 오버레이 없이 footer를 먼저 보여줬다.
- 복원 중 footer를 DOM에서 빼버리면 레이아웃 높이가 바뀌면서 브라우저가 다시 아래로 밀어냈다.
- 오버레이를 `useEffect`에서만 켜면 첫 페인트는 이미 지나간 뒤라 footer 플래시를 막지 못했다.
- `paint-lock`을 잘못 유지하면 `/` 같은 다른 라우트가 빈 화면으로 남았다.

이 과정에서 한 번은 `onRestoreComplete`를 인라인 콜백으로 넘긴 탓에 `Maximum update depth exceeded` 에러까지 터졌다.

원인은 명확했다.

- `ScrollManager`의 layout effect가 매 렌더마다 새로운 `onRestoreComplete` 참조를 보고 다시 돌았다.
- 그 안에서 `App`의 state가 갱신되면서 무한 재렌더가 생겼다.

결국 콜백을 `useCallback`으로 고정하고, 같은 상태면 다시 업데이트하지 않도록 막아 순환을 끊었다.

## 3. `/main` 해법 전환: 정확 복원보다 "새로고침 전용 오버레이"가 더 실무적이었다

여러 번의 분기 수정 끝에 결론은 명확해졌다.

`/main` 하드 리로드는 뒤로 가기 복원과 같은 방식으로 다루면 계속 흔들린다.

그래서 정책을 아예 분리했다.

- 뒤로 가기나 명시적 복원은 저장된 스크롤 값을 사용한다.
- 브라우저 새로고침은 별도의 로딩 오버레이를 쓴다.
- 오버레이가 돌고 있는 동안 뒤에서 메인 콘텐츠는 함께 렌더된다.
- 오버레이가 끝날 때는 `top 0`을 기준으로 보여준다.

이 전환이 중요했던 이유는 "정확한 이전 위치"보다 "이상한 장면을 먼저 보여주지 않는 것"이 이 화면에서 더 중요했기 때문이다.

실제 디버깅 일화도 이 결론을 강하게 만들었다.

- 휠을 한 번만 내린 뒤 새로고침하면 유독 footer 하단으로 튀는 케이스가 있었다.
- 휠을 두 번 내리면 오히려 잘 보이는 순간도 있었다.
- 결국 이는 브라우저 스크롤 앵커링과 동적 높이 변화가 섞인 타이밍 이슈였다.

이후에는 `/main` 비복원 리로드 동안 `scrollTop = 0`을 계속 고정하고, 오버레이가 떠 있는 동안에는 현재 문서 높이가 흔들려도 top에서 벗어나지 못하게 했다.

이 시점부터 체감 문제가 거의 사라졌다.

## 4. `/`는 px 복원보다 섹션 최소 복원이 맞았다

랜딩 페이지 `/`는 `/main`과 성격이 달라서 같은 해법을 쓰면 오히려 복잡도만 늘어났다.

그래서 `/`는 다음처럼 방향을 바꿨다.

- hero는 복원 대상에서 사실상 제외
- top10, pricing, faq, footer는 섹션 단위 최소 복원
- 새로고침과 POP 복원 모두 "절반 이상 넘어갔는가"를 기준으로 현재 섹션 결정
- 정렬은 `nav-h`와 `scroll-margin-top`을 반영해서 섹션 상단이 네비 아래에 붙도록 계산

여기서도 디버그 포인트가 있었다.

- top10 새로고침 시 제목이 네비에 잘려 보였다.
- 처음에는 단순히 `nav-h`만 빼서 정렬했는데, 실제 CSS의 `scroll-margin-top`이 더 큰 값을 쓰고 있었다.
- 이어서 `offsetParent` 체인으로 top을 계산하던 방식도 오차를 만들었다.

이 문제는 두 번 나눠 고쳤다.

- 섹션 복원 시 `scroll-margin-top`을 우선 사용
- 위치 계산은 `getBoundingClientRect()`와 현재 스크롤을 조합한 실제 레이아웃 기준으로 변경

결국 `/`는 정밀 scroll restore보다 "문서 흐름상 어느 섹션을 보고 있었는지"만 맞추는 쪽이 훨씬 안정적이었다.

특히 hero는 최상단 첫 인상 영역이라서, 조금만 어긋나도 복원보다 잘림이 더 거슬린다는 점을 다시 확인했다.

## 5. `/detail`은 기본 top-only, 단 새로고침에서만 trailer/row 조건부 복원

`/detail`은 처음에는 무조건 top으로 두는 편이 맞다고 판단했다.

하지만 실제 사용 흐름을 보면, trailer나 related row를 보고 있는 중 새로고침했을 때는 완전히 top으로 튀는 것도 어색했다.

그래서 최종 정책은 다음처럼 정리했다.

- 기본 동작은 `top 0`
- poster 클릭으로 다른 detail로 이동할 때도 상단으로 다시 올린다
- 다만 브라우저 새로고침에서만 예외적으로 복원
- `detail-trailer`나 `detail-row`가 이전 화면에서 절반 이상 보였을 때만 해당 래퍼의 최상단을 `nav` 아래로 맞춘다
- 조건이 맞지 않으면 항상 top으로 간다

이 부분도 한 번에 끝나지 않았다.

- detail 새로고침에서도 footer가 먼저 보였다가 위로 올라오는 플래시가 있었다.
- 오버레이를 `/detail/*` 시작 시에도 같이 렌더하도록 바꿔 이 문제를 가렸다.
- 그런데도 trailer/row 복원이 안 되는 경우가 있었는데, 나중에 보니 detail 내부 `useLayoutEffect`가 무조건 top reset을 덮어쓰고 있었다.
- 또 어떤 경우엔 `ScrollManager`가 target anchor가 아직 마운트되기 전에 복원을 끝내 버렸다.

그래서 아래 두 가지를 추가로 정리했다.

- 앱의 첫 진입이 `/detail`일 때는 top reset effect를 건너뛴다
- trailer/row anchor가 아직 없으면 복원을 완료 처리하지 않고 해당 앵커가 붙을 때까지 기다린다

이후에야 새로고침 후 오버레이가 사라질 때 trailer나 row 래퍼가 네비 아래에 안정적으로 붙기 시작했다.

## 6. 테스트 코드 작성 중 생긴 디버그 일화

이번 작업에서 느낀 점 중 하나는, 스크롤 복원은 체감 UX와 테스트 기대값이 아주 쉽게 어긋난다는 점이었다.

테스트 파일도 목적별로 다시 정리했다.

- `tests/main-scroll-restore.spec.js` -> `tests/main-route-scroll-policy.spec.js`
- `tests/scroll-restoration.spec.js` -> `tests/cross-route-scroll-policy.spec.js`

하지만 이름만 정리한다고 끝나지 않았다.

실제로 테스트를 만지면서 겪은 문제는 꽤 많았다.

### 6-1. Playwright는 실패하는데 수동으로는 정상처럼 보이는 순간들

가장 대표적이었던 것이 `/main`과 `/detail`의 리로드 시나리오였다.

- `/main`에서 스크롤 후 새로고침했을 때 수동 체감상은 정상인데, 테스트에서는 `scrollTop`이 여전히 `900`으로 남아 있다고 잡혔다.
- `/detail` row 복원도 수동으로는 괜찮은데, 테스트에서는 여전히 최상단으로 남았다고 실패했다.

나중에 보면 이 차이는 대부분 "오버레이가 언제 내려가느냐", "앵커가 언제 붙느냐", "테스트가 언제 측정하느냐"의 차이였다.

즉 화면은 정상처럼 보여도, 너무 이른 시점에 측정하면 아직 정책상 안정화가 끝나지 않은 순간을 잡아내곤 했다.

이 부분은 의도적으로 공백이 생기는 부분이 ui 상 좋게 형성된 실패 케이스다.

### 6-2. 셀렉터가 정책보다 먼저 낡아버리는 문제

한 번은 `demo-action-search` 셀렉터를 테스트가 더 이상 찾지 못했다.

원인은 테스트가 예전 UI 구조를 가정하고 있었기 때문이다.

이후에는 실제 UI 기준인 `.nav-mobile-search`로 셀렉터를 바꾸면서, 테스트도 정책뿐 아니라 현재 UI 구조를 따라가야 한다는 점을 다시 확인했다.

### 6-3. exact scroll 테스트는 새 정책과 충돌했다

기존 테스트 중 일부는 이런 전제를 갖고 있었다.

- `/detail` 새로고침 시 현재 스크롤 위치를 그대로 유지
- `/` 새로고침 시 현재 px 위치를 그대로 유지

하지만 오늘 정리한 정책은 그 방향이 아니다.

- `/detail`은 top-only 기반 + trailer/row 조건부 복원
- `/`는 섹션 최소 복원

그래서 테스트도 "이전 px 그대로"를 기대하면 계속 실패할 수밖에 없었다.

이 시점부터는 테스트가 구현을 끌고 가는 게 아니라, 정책에 맞게 테스트 기대값을 다시 써야 한다고 판단했다.

### 6-4. 디버깅 과정에서 콘솔 로그는 도움이 되지만 오래 두면 더 큰 노이즈가 된다

복원 흐름을 추적하려고 `AuthContext`, `ProtectedRoute`, 여러 페이지 컴포넌트에 디버그 로그를 심어 두었는데, 어느 순간부터는 로그가 너무 많아 실제 문제를 가렸다.

특히 React Strict Mode 환경에서는 같은 로그가 두 번씩 보여서 체감상 더 복잡해 보였다.

그래서 마지막에는 실제 오류 로그만 남기고 대부분의 `console.log`를 걷어냈다.

앞으로 테스트 과정과 디버깅 과정 중 생기는 로그는 주석처리를 하여 별도로 식별하고 테스트나 개발이 완료되면 주석을 없애는 습관을 기르도록 하자.

## 7. Firebase 설정과 보안 규칙 정리도 함께 진행함

오늘은 스크롤 복원 작업 외에도 Firebase 쪽 정리 작업을 꽤 많이 했다.

### 7-1. 클라이언트 설정을 env 기반으로 정리

처음 문제의식은 `src/firebase.js`에 Firebase 웹 설정이 하드코딩돼 있다는 점이었다.

이 값들은 비밀 키라고 보긴 어렵지만, 그래도 소스에 그대로 박아 두는 것보다 `env`로 빼는 편이 관리상 낫다고 판단했다.

그래서 Firebase 초기화는 `src/firebase/index.js`로 정리하고, 값은 `.env.local`과 `.env.example` 기준으로 관리하도록 바꿨다.

### 7-2. Firestore 규칙을 콘솔 전용이 아니라 repo 기준으로 옮김

이전에는 실제 규칙이 콘솔에만 존재해서 코드 기준 관리가 어려웠다.

그래서 아래 구조로 옮겼다.

- `firebase/firebase.json`
- `firebase/.firebaserc`
- `firebase/firestore.rules`

이후부터는 규칙도 코드처럼 버전 관리 가능해졌다.

### 7-3. `updates` 기능 제거

DB를 확인해 보니 `updates` 컬렉션은 더 이상 쓰지 않는 상태였고, 코드에도 업데이트 페이지 흔적이 남아 있었다.

그래서 아래를 정리했다.

- `updates` 컬렉션 관련 규칙 제거
- `/updates` 라우트 제거
- `UpdatePage`, `Update` 컴포넌트 삭제
- 콘솔에서도 `updates` 컬렉션 삭제

### 7-4. Firestore rules 실제 배포와 권한 확인

배포 전후로 가장 중요하게 본 것은 `feedback` 권한이었다.

- 읽기: 로그인 사용자만 가능
- 생성: 로그인 사용자만 가능
- 수정/삭제: 본인 글만 가능
- 관리자: 전체 삭제 가능
- 체험 계정: 읽기만 가능

실제로 DB를 재생성한 뒤 rules를 다시 deploy했고, 로컬에서 등록/수정/삭제/관리자 삭제까지 직접 확인했다.

### 7-5. Firebase 디버그 로그 위치 정리

`firebase deploy`를 루트에서 실행하니 `firebase-debug.log`가 루트에 떨어졌다.

이 로그는 Firebase CLI가 명령 실행 중 남기는 진단 로그라서, 실행 디렉터리를 기준으로 생성된다.

그래서 스크립트를 `cd firebase && ...` 형태로 바꾸고, 이후 새로 생기는 디버그 로그는 `firebase/firebase-debug.log` 안으로만 모이도록 정리했다.

## 8. 이번 작업에서 가장 크게 느낀 점

이번 작업의 핵심은 단순히 스크롤 값을 잘 저장하는 법을 찾는 것이 아니었다.

실제로 어려웠던 지점은 React 사이클과 브라우저 렌더 타이밍이 서로 얽히는 구간이었다.

아래와 같이 어려웠던 점을 설명

- 컴포넌트가 언마운트되었다가 다시 마운트되는 시점
- layout effect와 effect가 실제 첫 페인트 앞뒤에서 작동하는 차이
- 비동기 데이터가 늦게 붙거나, 붙은 뒤에도 동적 콘텐츠의 실제 크기가 나중에 확정되면서 문서 높이가 뒤늦게 다시 바뀌는 상황
- 브라우저의 스크롤 앵커링과 복원 시도가 코드와 충돌하는 순간

이 네 가지가 겹치면 "눈으로 보면 분명 footer를 찍었는데 코드상으론 top을 넣었다" 같은 장면이 생긴다.

그래서 이번 디버깅은 쉽지 않았다.

특히 리액트 라이프사이클만 봐서는 안 되고, 비동기 데이터 렌더 완료 시점과 실제 스크롤 컨테이너의 문서 흐름 변화까지 같이 봐야 했다.

결국 얻은 결론은 아래와 같다.

- 모든 화면을 exact scroll 복원으로 몰고 가려 하면 구조가 금방 복잡해진다.
- 라우트 성격에 따라 정책을 나누는 편이 낫다.
- `/main`은 새로고침 전용 오버레이
- `/`는 섹션 최소 복원
- `/detail`은 top-only를 기본으로 두고 예외만 조건부 허용

이렇게 나누고 나서야 복원 로직이 비로소 설명 가능한 구조로 정리됐다.

## 9. 마무리

오늘 작업은 "스크롤 복원 기능을 추가했다"기보다, 그동안 흩어져 있던 새로고침/뒤로가기/비동기 렌더/테스트 기준을 라우트별 정책으로 다시 정리한 작업에 가까웠다.

처음엔 Swiper 페이지 복원 하나를 고치려다가 시작했지만, 끝에 와서는 `/main`, `/`, `/detail`, Playwright 테스트, Firebase 설정, Firestore rules, 디버그 로그 위치까지 함께 정리하게 됐다.

가장 큰 수확은 두 가지다.

- 사용자가 실제로 거슬려하는 장면이 무엇인지 기준을 다시 세웠다.
- 복잡한 상태 관리 대신 각 화면에 맞는 복원 정책을 따로 두는 쪽이 더 유지보수 가능하다는 판단을 얻었다.
- 결국 이번 디버깅을 오래 끌고 가면서 느낀 점은, 스크롤 복원과 UX 개선은 무조건 더 정교하게 만드는 것이 답이 아니라는 것이다. 오히려 어떤 페이지에서 어떤 사용자 흐름을 지켜야 하는지 먼저 정하고, 그 목적에 맞게 설계하는 편이 더 중요했다. 이번에는 디테일한 복원에 집착하기보다, 각 화면의 성격에 맞는 최소한의 타협을 통해 더 안정적인 UX를 만드는 쪽이 현실적인 해법이었다.

오늘 정리한 구조는 이후 1.0.0까지 가져가도 설명이 가능한 형태라고 본다.
